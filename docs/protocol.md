# Lumen WebSocket Protocol

**Status:** Frozen for Sprint 1.
**Owners:** All three of us — do not change mid-sprint without telling the other two.

A single WebSocket connection per session, opened by the browser to `ws://<host>/ws`
(or `wss://` once we add TLS in Sprint 2). The server creates one `Session` instance
per connection and routes incoming messages by `type`.

We use **two channels over the same WebSocket**:

- **JSON text frames** carry control messages (events, FSM state updates, transcriptions, errors).
- **Binary frames** carry media payloads (JPEG image frames, Opus/WebM audio blobs, MP3 TTS).

To distinguish binary payload kinds, we prepend a **1-byte type tag** to every binary frame:

| Tag (uint8) | Direction       | Meaning                              |
| ----------- | --------------- | ------------------------------------ |
| `0x01`      | client → server | `frame` — JPEG bytes follow          |
| `0x02`      | client → server | `command_audio` — WebM/Opus bytes    |
| `0x03`      | server → client | `tts` — MP3 bytes follow             |

Everything else (state, transcription, errors, user events) is JSON text.

---

## Client → Server

### `user_event` (JSON)
Lifecycle events from the UI.

```json
{ "type": "user_event", "event": "start" }
{ "type": "user_event", "event": "stop" }
{ "type": "user_event", "event": "cancel" }
{ "type": "user_event", "event": "confirm" }
```

- `start`: user pressed Start. FSM transitions Idle → ListeningForCommand.
- `stop`: user pressed Stop. FSM transitions any active state → ReturningToIdle → Idle.
- `cancel`: user wants to abort the current task but stay connected. Same effect as `stop` for v1.
- `confirm`: user said "got it" / confirmed task completion (Sprint 3 will use this; Sprint 1 just logs).

### `frame` (binary, tag `0x01`)
A single JPEG-encoded camera frame. Quality 70, capture resolution 640×480.
Sent at ~5 FPS while in an active state (or always-on after Start in Sprint 1).

Wire format: `[0x01][...JPEG bytes...]`

### `command_audio` (binary, tag `0x02`)
A single WebM/Opus blob produced by `MediaRecorder` between PTT button down and up.
Server saves to `backend/captured_audio/<timestamp>.webm` (Sprint 1 inspection),
then transcribes via Whisper.

Wire format: `[0x02][...WebM/Opus bytes...]`

## Server → Client

### `fsm_state` (JSON)
Pushed whenever the FSM transitions. The client uses this to update the status indicator.

```json
{ "type": "fsm_state", "state": "idle" }
{ "type": "fsm_state", "state": "listening" }
{ "type": "fsm_state", "state": "object_active" }
{ "type": "fsm_state", "state": "nav_active" }
{ "type": "fsm_state", "state": "returning" }
```

State name mapping (server-internal → wire):
- `Idle` → `"idle"`
- `ListeningForCommand` → `"listening"`
- `ObjectAllocationActive` → `"object_active"`
- `NavigationActive` → `"nav_active"`
- `ReturningToIdle` → `"returning"`

### `transcription` (JSON)
Sent after Whisper transcribes a `command_audio` blob. Useful for client-side debugging
display and audit.

```json
{ "type": "transcription", "text": "find my cup", "confidence": 0.92 }
```

`confidence` is a heuristic in `[0, 1]` derived from Whisper's average log-probability.
It is approximate; do not gate critical logic on a hard threshold.

### `tts` (binary, tag `0x03`)
An MP3-encoded TTS clip generated by gTTS. Client appends to its audio playback queue.
Clips never overlap.

Wire format: `[0x03][...MP3 bytes...]`

### `error` (JSON)
Non-fatal errors the user might want to see (e.g. transcription failed, parser couldn't
understand). Fatal errors are signaled by closing the WebSocket.

```json
{ "type": "error", "code": "transcription_failed", "message": "Couldn't understand audio." }
{ "type": "error", "code": "parse_unknown", "message": "I didn't catch that, please repeat." }
```

Defined error codes:
- `transcription_failed` — Whisper raised or returned empty.
- `parse_unknown` — parser returned `task_type: "unknown"`. Usually accompanied by a
  clarification TTS (`"I didn't catch that, please repeat"`) on the audio channel.
- `audio_decode_failed` — server couldn't decode the WebM/Opus blob to PCM.
- `protocol_violation` — client sent something we couldn't parse. Ignored, but reported.

---

## Out-of-Protocol Messages

The server **logs and ignores** any message it can't parse — JSON without a `type` field,
binary frames with an unknown leading tag, etc. This keeps the contract conservative.
The server may also emit an `error` with code `protocol_violation` for visibility.
